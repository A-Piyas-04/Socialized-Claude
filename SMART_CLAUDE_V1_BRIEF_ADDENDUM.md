# TRACK A0 — Zero-cost automated collection and scoring

No paid API key is available. This track uses the user's existing Claude subscription via Claude Code, plus a free-tier non-Anthropic judge. Everything here is scripts; nothing asks the user to copy, paste, or rate anything.

## A0.1 What this measures, and what it does not

State this at the top of every output file and in the harness README, because the project's prior failure was exactly this kind of slippage:

- Responses are generated by **Claude Code**, not claude.ai and not the Claude API. The three surfaces have different system prompts and scaffolding. These results characterise the **skill text**, not claude.ai behaviour. Activation rates in particular do not transfer.
- The judge is an automated model. Its scores are a **screening instrument**, not the human evaluation that `evaluation/EVALUATION_PLAN.md` specifies. It never feeds S1–S7.

## A0.2 Collection harness

New `scripts/collect_cc.py`. Drives `claude -p` over the run sheet.

**Auth.** Require `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`). **Abort with a clear error if `ANTHROPIC_API_KEY` is set in the environment** — in `-p` mode a set API key always takes precedence and would bill the user. Do not silently unset it; tell them.

**Per-row invocation:**

```
claude -p <message> --output-format stream-json --verbose --model <model>
```

**Arm control.** The skill-on arm needs no upload: place the built skill at `.claude/skills/explanation-lab/SKILL.md` in a scratch working directory. For skill-off arms, pass `--settings` with `skillOverrides: {"explanation-lab": "off"}`.

**Verify the arm you actually ran.** The documentation does not explicitly confirm that `skillOverrides` is honoured when passed through `--settings`. Do not trust the flag. Parse the `system/init` event from the `stream-json` output, record the tools and skills it reports, and **fail the row if the observed arm does not match the intended arm.** Write the observed value into the run sheet's existing `activation_evidence` column. Build this check first and run a two-row smoke test before any full sweep — if `skillOverrides` turns out not to be honoured, the fallback is two separate working directories, one containing the skill and one not, which is unambiguous.

**Resumability.** Write each response to `responses/<row_id>.md` immediately and skip rows whose response file already exists. The sweep consumes subscription quota and will hit limits; it must survive being killed and restarted. On a rate-limit error, back off and retry with a cap, then record the row as incomplete rather than aborting the run.

**Fill the run sheet.** `date`, `surface` (`claude-code`), `model_label`, `activation_observed`, `activation_evidence`, `operator` (`collect_cc`). These columns already exist and `summarize_results.py --check-only` already validates them.

**Sampling.** Default 3 samples per cell. The archive had one sample per cell and therefore no variability estimate at all; this is the cheapest available fix. Make it a flag.

Add a `--dry-run` that prints the planned invocations and the estimated row count without calling anything.

## A0.3 Judge pipeline

New `scripts/judge.py`. Default backend: Google AI Studio free tier, configured by env var, with the backend abstracted behind one interface so it can be swapped. No key in the repo, no key in any output file.

Three tasks, in increasing order of trustworthiness:

**1. Critical-fact extraction (most trustworthy — treat as the primary signal).**
`TEST_CASES.json` already carries `critical_facts` and `common_misconceptions` per case. Ask, per response: which of these facts does it state, and does it assert any of these misconceptions? This is near-objective and maps directly onto the existing rubric §B coding. It is the **comprehension-class** measure.

**2. Forced-choice pairwise preference.**
Never ask for an absolute 1–5 score. The archive's judge gave 5/5 on all nine dimensions to all 30 answers — a total ceiling. Pairwise has no ceiling. Required controls:
- Randomise presentation order.
- **Run every pair in both orders.** Discard pairs where the verdict flips, and report the flip rate as a headline number — it is the judge's own reliability estimate.
- Strip anything identifying the condition before presenting.

**3. Per-dimension pairwise** on `navigability` and `register_fit` only, same both-orders control. Do not attempt the other nine dimensions automatically.

**The analysis that matters.** Report fact capture and pairwise preference in **separate tables, never combined into one score.** The finding to look for is the one the project most needs and is least equipped to see: *preference up, fact capture flat or down* means the presentation operations bought fluency rather than understanding. Make that comparison the first thing `summarize_results.py` prints for any presentation variant.

**Calibration.** The harness cannot establish its own validity. Emit `evaluation/judge_calibration_set.md`: 20 responses sampled across conditions, with the judge's verdicts withheld in a separate file. If the user ever wants a validity estimate, scoring those 20 by hand gives an agreement rate. Do not block anything on this and do not ask them to do it.

## A0.4 Comprehension item screener

New `scripts/screen_items.py`. Fixes E5's fatal flaw, which was that the no-explanation control answered 15/15 and the study therefore had zero diagnostic power.

For every item in `evaluation/comprehension/ITEM_BANK.json`, query the judge model **with no explanation text**, several times. Any item answered correctly without reading anything is non-diagnostic — flag it, emit the surviving set to `evaluation/comprehension/ITEM_BANK_screened.json`, and report the survival rate.

Also flag items that are pure recall. The Choi (2023) paper in the project's sources found the model performed markedly worse on problem-solving items than on recall and interpretation items, which is the discrimination you want. The audit already notes that the item labelled `C_transfer` for databases is recall in disguise. If few or no items survive screening, that is a real and useful result: say so in the output rather than lowering the bar.

## A0.5 Track A0 definition of done

- `collect_cc.py` runs a 2-row smoke test, correctly refuses to run with `ANTHROPIC_API_KEY` set, and correctly fails a row whose observed arm disagrees with the intended arm.
- A full `pilot16` sweep completes, is resumable, and passes `summarize_results.py --check-only`.
- `judge.py` produces fact-capture and pairwise tables with the order-flip rate reported.
- `screen_items.py` reports the diagnostic survival rate.
- Every output file carries the surface and instrument disclaimers from A0.1.
- No key, token, or credential appears in the repo, in any committed output, or in any log.

# A10 — Operations and rules missed in the first brief

Reviewing all seven source documents against the Track A plan, these are not covered. Items 1 and 2 are the largest omissions.

## A10.1 Instruction persistence (new `op:persistence`)

**Source evidence.** This is one of the two most-repeated complaints in the user corpus and nothing in V1 addresses it. Reported verbatim patterns: "Standard Technical English works for a minute before it's back to its old tricks"; concise output mode "made absolutely zero difference"; "constantly ignoring its core instructions, apologising for it and immediately breaking them again."

Note that this is **distinct from repair** (A4). Repair is about re-reading a clarification. Persistence is about a constraint stated once at turn 2 still holding at turn 20.

Rules:

- A constraint the person states about *how* to respond — length, register, vocabulary, format, what to omit — applies to every later turn until they change it. It is not scoped to the turn that stated it.
- Re-check standing constraints before sending, not only when the person repeats them. Having to restate a constraint is a failure.
- When a constraint and the current request genuinely conflict, say so in one clause and ask, rather than silently dropping the constraint.
- Never treat a long or complex question as licence to exceed a stated length limit.

Add to `VARIANTS` as `persist`. Add a `persistence` test category: multi-turn cases that state a constraint at turn 1 and check it at turns 3 and 5, with an intervening topic shift.

## A10.2 Work-reporting contract (new `op:work-report`)

**Source evidence.** The clearest positive specification anywhere in the corpus — a practitioner stating exactly what they want instead of elaborate terminology: say what you changed, why you changed it, what you did not verify, and where you need my input. Alongside it, the failure case: a model that announced a file change, did not make it, and admitted it only when asked. This is the highest-value addition for the professional users the corpus describes, and V1 has nothing on it.

Rules, applying when the response reports on work performed rather than explaining a concept:

- Lead with what changed, concretely and by name. Not what was attempted or intended.
- State what was **not** verified, and what would verify it.
- State explicitly where a decision is needed from the person, separated from the report.
- Never describe an intended action as a completed one. If a step was planned and not done, say it was not done.
- Report a failure as its own statement, not folded into a narrative of progress.
- No tallies of past mistakes, no promises about future behaviour, no apology paragraphs. State the correction and move on.

Add a `work_report` test category. This operation interacts with Claude Code usage specifically, which makes it directly checkable in the A0 harness.

## A10.3 Scope discipline — fold into `op:register` or its own block

**Source evidence.** "Sometimes it will add unnecessary steps when I give it a full prompt kit to work off of"; "relying too much on memory than what I am clearly asking it to do"; "that's an extremely ambitious task" preambles on simple requests. The existing `responsiveness_to_intent` rubric dimension measures this, but no operation instructs it.

Rules: do what was asked and nothing adjacent; do not add steps to a specification the person supplied; do not open by characterising the task's difficulty or ambition; a request that is clear does not need a preamble.

## A10.4 Citation and attribution integrity — extend the accuracy rules

**Source evidence.** The Choi (2023) BMC Medical Education study in the project's own sources found **incorrect citations for 69.7% (191/274) of responses** — while rationales were correct 77.8% of the time. Fluent, well-reasoned, correctly-structured output with fabricated supporting references. Independently, the user corpus complains about "name-dropping scholars and advanced or foreign terminology without explaining them."

V0's accuracy rules forbid inventing a mechanism, number, study, date, or historical claim. They do not address citations as a distinct and much higher-frequency failure. Add:

- Do not produce a specific citation — author, title, year, section, page — unless you are confident it exists as stated. Describe the finding and say it is from the literature instead.
- Naming a researcher or a paper without saying what they actually showed adds no information. Either explain the finding in the same sentence or omit the name.
- Do not use a foreign-language or field-specific term without glossing it where it first appears.

This matters more once presentation is unlocked: structure raises perceived authority, which raises the cost of fabricated support.

## A10.5 Presentation guards the first brief omitted

**Source evidence.** The counter-signal in the corpus — a user who prefers Claude specifically and dislikes ChatGPT's heavy whitespace and emoji use. The first brief's decorative-structure flags do not cover either.

Add to the `op:presentation` anti-patterns, and to the linter's `decorative_structure_flags`:

- **Emoji as structure.** No emoji as bullet markers, section icons, or status indicators.
- **Whitespace padding.** Single-sentence paragraphs used throughout where the sentences form one continuous argument. A unit break should mark an idea break, not a line break.
- **Empty transitional units.** A paragraph whose only content is announcing the next paragraph.

Also add the positive case the first brief underweighted, prompted by the GPT-6 "Intelligent UI" capture: when a comparison has three or more items across two or more dimensions, a table is the correct form and prose is the wrong one; when a flow branches, a diagram in a fenced block is the correct form. State these as *defaults for those shapes*, not as options — otherwise the model keeps choosing prose, which is the failure V1 exists to fix.

## A10.6 Re-ask rate as a first-class target

The first brief put the re-ask counter only in the browser extension. It belongs in the methodology.

State in `COMMUNICATION_GRAMMAR.md` that the project's primary real-world success signal is **the person not having to ask again** — the corpus reports needing one or two rewrites per long output, and that is the cost the project exists to remove. The A0 harness can approximate it on the multi-turn `follow_up`, `repair`, and `persistence` cases: whether turn 2 is a clarification of the same request or a new one. Add it to the summary output.
