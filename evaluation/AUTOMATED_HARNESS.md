# Automated harness (Track A0)

**What this measures, and what it does not.**

- Responses are generated by **Claude Code** (`claude -p`), not claude.ai and not the Claude
  API. The three surfaces have different system prompts and scaffolding. These results
  characterise the **skill text**, not claude.ai behaviour. Activation rates in particular do
  not transfer.
- The judge is an automated, non-Anthropic model. Its outputs are a **screening instrument**,
  not the human evaluation that `EVALUATION_PLAN.md` specifies. They never feed S1–S7.
- The judge is a **regression guard** for changes to Claude's explanations. Every comparison is
  Claude against Claude; Claude-vs-GPT is not part of the evaluation. Fact capture is the primary
  measure and is never combined with pairwise preference.

Nothing here asks a person to copy, paste, or rate anything.

## Setup (once per shell)

| Variable | Source | Used by |
|---|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` | `claude setup-token` (Claude subscription); one line, `sk-ant-oat01-…` | `collect_cc.py` |
| `GROQ_API_KEY` | console.groq.com, free tier | judge (default backend) |
| `GEMINI_API_KEY` | Google AI Studio, free tier | judge with `JUDGE_BACKEND=gemini` (Gemma fallback) |
| `JUDGE_BACKEND`, `JUDGE_MODEL` (optional) | defaults `groq`, `openai/gpt-oss-120b` | judge backend |

Gemini's free tier caps each model at 20 requests per day per project, far below a sweep's
judge volume, so Gemini is a fallback only.

## Judge acceptance (required before any sweep is judged)

```
python scripts/judge_acceptance.py      # research/judge_acceptance/<backend>-<model>.md
```

Claude-vs-Claude pairs only (the archive's Claude answers under different prompt styles, and
later V0 vs V1 via `--run`/`--pair`), plus a floor of deliberately degraded answers (truncated, a
fact removed, the answer buried at the end). A judge is accepted only if its order-flip rate is
at most 0.20 **and** it passes the floor in both pairwise preference and fact capture. A
consistent judge can still be useless; the floor catches that.

Set them in the shell environment only, never in a file in the repository. `collect_cc.py`
refuses to start while `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` is set, because a set key
takes precedence over the subscription in `-p` mode and would be billed. It does not unset
them for you.

## Commands

```
python scripts/collect_cc.py --smoke                                    # arm check + 2 rows (skill off, skill on)
python scripts/collect_cc.py evaluation/runs/pilot16-cc --check-arms    # arm check only; no quota used
python scripts/collect_cc.py evaluation/runs/pilot16-cc --dry-run       # planned invocations; nothing called
python scripts/collect_cc.py evaluation/runs/pilot16-cc                 # sweep; rerun the same command to resume
python scripts/summarize_results.py evaluation/runs/pilot16-cc --check-only
python scripts/judge.py evaluation/runs/pilot16-cc                      # fact capture, pairwise, 2 dimensions
python scripts/judge.py evaluation/runs/pilot16-cc --calibration        # evaluation/judge_calibration_set.md
python scripts/screen_items.py                                          # evaluation/comprehension/ITEM_BANK_screened.json
```

New runs: `--create --subset pilot16 --samples 3` (3 samples per cell by default).

## How the arm is controlled and verified

Each row runs in a fresh sandbox outside the repository with its own `CLAUDE_CONFIG_DIR`, so
user-level skills, CLAUDE.md, memory and plugins are absent in every arm. The batch's built
ZIP is installed as a project skill; skill-off rows pass
`--settings {"skillOverrides": {"<skill>": "off"}}`, where `<skill>` is the id in that run's frozen manifest (`socialized` for a new run, `explanation-lab` for `pilot16-cc`). Tools are `Read,Skill` with
permission mode `dontAsk` in every arm.

The flag is not trusted. The `system/init` event is parsed for every row, and the row fails
(the process is killed) if `init.skills` disagrees with the intended arm, if `apiKeySource` is
not `none`, or if the tool set differs. A skill-off row also fails if it calls the Skill tool
on the skill or reads any of its files. The observation is written to `activation_evidence`
and `cc_meta/<row_id>.json`. `--check-arms` performs the same check with the token withheld,
so it cannot spend quota.

## Outputs

| File | Contents |
|---|---|
| `runs/<id>/responses/<row_id>.md` | response text only |
| `runs/<id>/cc_meta/<row_id>.json` | observed init state, tool calls, status, usage |
| `runs/<id>/COLLECTION_NOTICE.md` | the disclaimers above plus collection settings |
| `runs/<id>/judge/fact_capture.csv` | facts stated and misconceptions asserted, per response |
| `runs/<id>/judge/pairwise.csv` | every pair in both orders, with flips marked |
| `runs/<id>/judge/judge_summary.md` | separate fact-capture and preference tables, flip rates |

Fact capture (comprehension-class) and preference (preference-class) are never combined.
`summarize_results.py` prints the preference-versus-fact-capture comparison first when judge
output exists; a flag there means preference rose while fact capture was flat or lower.
